# ADR: Agent 即操作者（上下文，不是给人用的控制面板）

- 状态：已接受
- 日期：2026-09-01

## 背景与约束

yoi 覆盖的问题空间接近宝塔：自己的 Linux、一套完整部署栈、要装、要看、
要改。宝塔把复杂度藏进 GUI，让人点。

编码 Agent 已经能在用户授权下执行命令。再做一套「简化操作」的面板，
是把操作者设错了。人要的是对 Agent 说话；Agent 要的是稳定、可读、
可写回的上下文。

已有约束（见 `docs/adr/agent-data-model.md`、
`docs/prd/dashboard.md`）：

- Dashboard 只读，写入口是 `yoi-server` / `yoi`。
- 上下文层不校验 Plan、不编排、不拦危险操作。
- Pack 投递是 skill 内 HTTP，不依赖 CLI。
- 人在环：安装前询问，pack cmdspec 等人打 yes。

## 决策

1. **操作者是用户的编码 Agent**，不是人点的面板。人的最终界面是自己
   Agent 的聊天框。yoi 不实现聊天产品。
2. **产品交付的是上下文，不是操作简化。** 身份、意图、事实、现场
   （Service / Release / Event / live）必须对人可读、对 Agent 可解析。
   复杂度展开给 Agent，不收进菜单。
3. **Dashboard 是探针与审计面。** 给人瞥一眼和核对 Agent 做了什么。
   不在此版或后续定位里长成启停 / 建站 / 改配置的控制面。
4. **两个 CLI 是 Agent 的系统调用**，不是给人日常敲的主 UX。
5. **商店与 Pack 是软件源。** skill 是进这个 OS 的壳与路由，不是被出售
   的产品本体。

## 备选方案

- **宝塔式人用面板**：功能按钮覆盖安装、启停、文件、定时任务。否决：
  与「Agent 代管」相反，且会把 Dashboard 从探针拖成控制面。
- **只做技能商店**：产品停在「一句话装 Pack」。否决：实现重心已在账本
  与探针；商店是源，不是 OS。
- **yoi 自有聊天 UI**：自建对话壳，Agent 当后端。否决：人已经有编码
  Agent；再做一个聊天框是重复壳，且把操作面从用户的 Agent 挪走。
- **控制面（启停 / 回滚 / 策略引擎）**：yoi 执行变更。否决：与「记录
  事实、不编排」冲突；策略和执行留在 Agent 与人在环。

## 权衡与后果

- **没有给人的操作捷径**：不会用过宝塔的人不能靠点按钮完成变更，必须
  通过 Agent。这是刻意的。
- **上下文质量即产品**：`~/.yoi/` 写得不全（例如有 Service 无
  `runtime`），Dashboard 只能「无法探测」。登记手续见
  `docs/prd/os-registration.md`；瘦记录仍是合法空态，不是本 ADR 的失败。
- **Dashboard 保持瘦**：可以加深观察（指标、时间线、合成状态），不能
  用「用户也想点一下」为理由加控制按钮。
- **商店文案可以继续讲第一条命令**（装 skill、说一句话），但内部文档
  与 README 的产品定义必须是 OS，避免再漂回「我们是商店」。

## 边界与失败

- 人拒绝确认时，不得安装或变更。yoi 不提供「跳过 Agent、在面板里完成
  同等变更」的后备 UX。
- Agent 崩溃或撒谎时，账本可能不一致；yoi 不靠状态机挽救，只保证写下
  去的是文档、读得出来。
- 多机切换与聚合是 Agent 的责任，不是 Dashboard 的责任。

## 验证

- 新功能质问时，若要把 Dashboard 做成控制面或把商店写成产品本体，必须
  先废止或修订本 ADR。
- 公开文档（README）与 `docs/spec.md` 称 yoi 为部署栈 OS，称商店为软件
  源，称操作者为用户的 Agent。
