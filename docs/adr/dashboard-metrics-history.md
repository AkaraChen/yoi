# ADR: Dashboard 指标历史（内存环形缓冲）

- 状态：已接受
- 日期：2026-08-27

## 背景与约束

PRD 初版把「历史趋势」列为非目标，留待后续设计。2026-08-27 用户评估后
决定做时间窗口趋势图，约束：不引入用户需要额外安装的服务，尽量单进程
解决；先简单，等用户反馈再演进。

## 决策

1. **内存环形缓冲**：探针进程内一个采样 goroutine，每 5 秒采集一次完整
   指标快照（复用 gopsutil 采集函数），追加到定长环形缓冲，容量 720 点
   （= 最近 1 小时）。内存占用为数百 KB 量级。
2. **历史 API**：`GET /api/server/history` 返回
   `{ intervalSec: 5, points: [...] }`，每点含 ts、cpuPercent、memPercent、
   netUpRate、netDownRate、load1——只投影图表需要的字段。
3. **当前值 API 复用采样结果**：`GET /api/server/metrics` 返回环形缓冲中
   的最新快照，不再在请求时现采（CPU 使用率与网络速率的差分语义天然
   契合固定周期采样）。进程启动时先同步采一个点再对外服务。
4. **前端**：服务器概览页加「趋势（近 1 小时）」区块，SVG 面积图
   （零依赖自绘，accent 令牌着色），5 秒轮询历史接口。
5. **不持久化**：探针重启历史清零，这是已接受的行为。

## 备选方案

- **纯 Go SQLite（modernc.org/sqlite）落盘**：重启后历史保留，但引入
  写盘 IO、retention 清理与 schema 管理，违背「先简单」。若用户反馈
  需要跨重启历史，可作为纯增量追加（采样点模型不变）。暂缓。
- **in-process Redis**：不存在生产级实现（miniredis 是测试替身，
  ledisdb 停更）；且时间序列环形数据用 Go 切片表达更直接，Redis 数据
  结构在进程内没有生态位。否决。
- **请求时现采 + 前端自己存点**：前端刷新/换页即丢历史，且 CPU/网络
  差分指标依赖稳定采样周期。否决。

## 权衡与后果

- 探针停机期间的指标缺口直接可见（历史从重启后开始），符合探针定位；
  长期留存是 Prometheus 一类系统的职责，不是本面板的目标。
- 采样周期与容量是常量（5s × 720）；变更需改代码发版，暂不提供配置项。
- 趋势图只覆盖 CPU/内存/网络/负载；磁盘等慢变指标不出图。

## 验证

- 探针运行数分钟后 `GET /api/server/history` 返回按时间升序的点列，
  点间隔约 5 秒，容量封顶 720。
- 概览页趋势图随轮询持续右移；重启探针后历史从空重新累积。
